# Architecture

## Overview

Implement the following event-driven architecture.

```text
                         ┌──────────────────┐
                         │  Producer Service │
                         │                  │
                         │  Join City Group │
                         │      Form/API    │
                         └────────┬─────────┘
                                  │
                                  ▼
                         ┌──────────────────┐
                         │   Message Queue  │
                         │ / Event Topic    │
                         │ CityGroupJoined  │
                         └───────┬──────────┘
                                 │
                ┌────────────────┼────────────────┐
                │                │                │
                ▼                ▼                ▼
        ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
        │   Airtable   │ │    Brevo     │ │   Supabase   │
        │   Consumer   │ │   Consumer   │ │   Consumer   │
        │              │ │              │ │              │
        │   Adapter    │ │   Adapter    │ │   Adapter    │
        └──────────────┘ └──────────────┘ └──────────────┘
```

## Responsibilities

### Producer

The producer:

1. Accepts a city-group join submission.
2. Validates the input.
3. Creates a `CityGroupJoined` event.
4. Publishes the event to the message queue/topic.

The producer must not call Airtable, Brevo, or Supabase directly.

### Message queue

The queue/topic is responsible for distributing the event to independent consumers.

Each destination consumer must be able to process the event independently.

A failure in one consumer must not prevent another consumer from processing the same event.

The candidate may choose an appropriate lightweight messaging technology unless otherwise agreed. The choice and local setup should be documented.

### Consumers

Each consumer has exactly one destination responsibility:

- Airtable consumer → Airtable
- Brevo consumer → Brevo
- Supabase consumer → Supabase

A consumer:

1. Receives a `CityGroupJoined` event.
2. Transforms the event into its destination-specific representation.
3. Calls the destination API.
4. Acknowledges the message only after successful processing.
5. Retries retryable failures.
6. Handles exhausted retries according to the selected queue technology.

## Retry behaviour

The implementation must support:

- Configurable maximum attempts.
- Retry of failed processing.
- No acknowledgement before successful processing.
- A clear outcome when retries are exhausted.

If the selected messaging technology supports dead-letter queues, the candidate may use that facility.

The candidate should also consider duplicate delivery and explain how their implementation behaves in that situation.

## Data contracts

The canonical event is:

```json
{
  "event": "CityGroupJoined",
  "eventId": "generated-unique-id",
  "timestamp": "2026-11-16T10:30:00Z",
  "data": {
    "name": "Jane Doe",
    "email": "jane@example.com",
    "city": "London",
    "country": "United Kingdom",
    "interests": ["Technology", "Climate"]
  }
}
```

### Producer input

```json
{
  "name": "Jane Doe",
  "email": "jane@example.com",
  "city": "London",
  "country": "United Kingdom",
  "interests": ["Technology", "Climate"]
}
```

### Airtable

Table: `City Group Members`

| Field | Type |
|---|---|
| `Name` | Single line text |
| `Email` | Email |
| `City` | Single line text |
| `Country` | Single line text |
| `Interests` | Long text |
| `Event ID` | Single line text |

### Supabase

Table: `city_group_members`

| Column | Type | Required |
|---|---|---:|
| `id` | uuid | Yes |
| `name` | text | Yes |
| `email` | text | Yes |
| `city` | text | Yes |
| `country` | text | Yes |
| `interests` | jsonb | No |
| `event_id` | text | Yes |
| `created_at` | timestamptz | Yes |

`id` and `created_at` may be generated by Supabase.

### Brevo

| Attribute | Source |
|---|---|
| `EMAIL` | `email` |
| `NAME` | `name` |
| `CITY` | `city` |
| `COUNTRY` | `country` |

`interests` does not need to be sent to Brevo.

## Architectural constraints

- Keep the producer independent from destination APIs.
- Keep each consumer responsible for one destination.
- Keep destination-specific transformation inside the corresponding consumer.
- Do not couple the consumers to one another.
- Do not require a production deployment.
- Do not introduce infrastructure that is disproportionate to the exercise.
